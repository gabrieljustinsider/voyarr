# Restricted Terminology & Vocabulary Governance (Fleet-Wide Law)

The following internal engineering, infrastructure, and technical terms MUST NEVER be exposed or rendered in user-facing UI screens, modal titles, button labels, descriptions, toast alerts, placeholders, error toasts, or client-side marketing copy. Always use user-centric, brand-aligned terminology instead:

- **'fleet' / 'fleet-wide'**: Use *'Network'*, *'Ecosystem'*, *'Apps'*, *'Services'*, *'Console'*, *'Workspace'*, *'Account'*, or the application's proper brand name.
- **'bots'** (when referring to applications or system services): Use *'Apps'*, *'Services'*, *'Tools'*, or *'Assistants'*.
- **'worker' / 'durable object' / 'do'** (in UI alerts or status badges): Use *'Service'*, *'Sync Engine'*, *'Background Task'*, or *'Processing Engine'*.
- **'neon' / 'postgres' / 'drizzle' / 'sql'** (in end-user notices): Use *'Database'*, *'Cloud Storage'*, or *'Secure Vault'*.
- **'hono' / 'router' / 'api route'**: Use *'Server'*, *'Cloud Service'*, or *'Endpoint'*.
- **'kv' / 'r2' / 'd1'** (in customer error states): Use *'Cloud Storage'*, *'Cache'*, or *'Asset Storage'*.
- **'raw stack traces' / 'unhandled exception errors'**: Must be caught by Error Boundaries and rendered as user-friendly incident reference cards.

- **Opportunistic Abstract Refactoring**: Whenever logic or code is being added or modified, if it can be abstractly refactored to increase code quality, DRY principles, and modularity without introducing sacrifices in performance, readability, or complexity, always opt for abstract refactoring.
- **No Forced Abstractions**: Never force abstract refactoring. If abstraction does not make logical sense, introduces unnecessary layers, complicates debugging, or risks stability in a specific code block, keep the implementation concrete.
- **Zero Native Browser Dialogs (Fleet-Wide Law)**: Under NO circumstances should native blocking browser dialogs (`window.alert()`, `window.confirm()`, or `window.prompt()`) ever be used.
  - **Informational Notices**: Use dismissable toasts (`toast.success()`, `toast.error()`, `toast.info()`).
  - **Destructive & Operational Confirmations**: Confirmation prompts (deleting resources, revoking credentials, rebooting nodes, or unlinking records) MUST use styled **action snackbars** or in-app confirmation dialogs equipped with explicit inline `[Cancel]` and `[Confirm]` action triggers.
  - **User Input & Prompts**: Never use `window.prompt()`. Always collect user input via styled modal dialogs or inline form components.
- **Toggle Switch Container & Indicator Alignment (Fleet-Wide Law)**: Whenever building toggle switches using checkbox inputs and Tailwind pseudo-elements (`after:absolute`, `after:top-...`, `after:left-...`), the toggle track pill element (`<div>`) MUST ALWAYS explicitly include `relative`. Without `relative` on the track itself, the indicator dot / knob positions relative to an outer parent container rather than staying confined within the toggle track pill.
- **Theme-Aware Contrast Governance (Fleet-Wide Law)**: Variable background tokens (`bg-primary`, `bg-secondary`) must NEVER be paired with hardcoded static text colors (such as `text-white` or `text-black`). When theme palettes support dynamic, multi-theme, or light primary accents in dark mode, interactive controls (buttons, badges, pills) MUST use semantic foreground tokens (`text-btn-primary`, `--primary-foreground`, or component wrappers). Global stylesheet safeguards (`.bg-primary { color: ... }`) must also be maintained to invert text and icon colors on light/white primary themes (e.g. Carbon, Blood) to prevent unreadable white-on-white rendering.
- **Dynamic Accent Shadow & Glow Governance (Fleet-Wide Law)**: Ambient drop-shadows, focus rings, and glow effects on active or interactive elements MUST use variable opacity tokens (e.g. `shadow-primary/20`, `ring-primary/30`, or CSS variables `rgba(var(--primary-rgb), 0.25)`) instead of hardcoded hex or RGB color channels (such as `rgba(16,185,129,0.2)` or `shadow-emerald-500/20`). This ensures glow signatures dynamically match the active theme palette.
- **Paired Theme Alpha Tokens & Container Contrast (Fleet-Wide Law)**: Subtle tinted containers (chips, metric badges, info cards, callouts) using accent tints (`bg-primary/10`, `border-primary/20`) MUST pair with semantic accent text (`text-primary` or `text-text-main`) with a minimum 4.5:1 WCAG AA contrast ratio against `bg-dark` across every registered theme palette. Never pair subtle background tints with muted, low-saturation text that washes out on non-default themes.
- **SVG Stroke & Fill Color Inheritance (Fleet-Wide Law)**: SVG icons embedded within buttons, interactive chips, and theme-colored badges MUST use `currentColor` for strokes and fills (or omit hardcoded color overrides). They must rely on parent typographic color inheritance rather than hardcoded `text-white` or `text-black` utility classes, ensuring icons invert and remain visible across all theme states.
- **Theme Token & Storage Parity (Fleet-Wide Law)**: All frontend web applications must standardize on the root document attribute `data-theme="<theme_id>"` and mirror active theme selection in persistent storage under a standardized key (`ledger_theme` / `fleet_theme` / broadcast channel `fleet-theme-change`). The foundational token set (`--primary`, `--secondary`, `--bg-dark`, `--card-bg`, `--glass-border`, `--text-main`, `--text-secondary`, `--text-muted`) must exist with parity across application stylesheets.
- **Engineering Principles**: Always prioritize methods of coding that are highly efficient, secure, stable, and follow best-practices.
